1 · What the player already is — and why it constrains PiP

The Player (src/renderer/src/screens/Player.tsx) is not one <video>. It is a stage holding two stacked VideoSurface elements: the one on air, and a hidden standby that starts buffering the next pick thirty seconds before the end. An episode handoff is a swap — the standby is promoted with its buffer and its ffmpeg pipe intact — not a load. Seeking is a new stream URL (/stream/<id>?t= restarts ffmpeg at -ss), because the remux/transcode paths are unseekable pipes played through MediaSource. Fullscreen is requested on the stage wrapper, never on a video, precisely so the swap can't tear it down.

Each of those decisions constrains this feature:

  • PiP is per-element, but our element changes identity at every handoff. Whatever floats the video must follow the swap or the PiP window dies at each episode boundary — the exact failure mode fullscreen-on-the-stage was designed to avoid, back to bite us in a place where there is no stage to target.
  • Seek and Retry re-attach src on the same element. PiP must survive a source swap on the element it is showing.
  • The standby must never end up in PiP. It is muted, refuses to play, and exists only to hold a buffer.

2 · Two candidate APIs, one spike, one verdict

Chromium offers two PiP APIs. Document PiP (documentPictureInPicture.requestWindow()) floats an arbitrary DOM subtree — it could have carried the whole stage, both surfaces and our OSD, and made the handoff question vanish. Element PiP (video.requestPictureInPicture()) floats one video element inside a Chromium-owned window with Chromium-owned controls. The choice is not ours to make on taste: it turns on what this Electron build actually implements, so the spike ran first (/tmp/pip-spike, runnable on demand — two generated test clips, both APIs exercised with and without user gestures).

The timeline that has to work

One diagram carries the whole design: what each surface is doing around an episode boundary, and who owns the PiP session at each moment. The transfer at the swap is legal only because a session already exists (R2 + R5) — which is why the controller must never exit the old session before requesting the new one.

3 · The UX — try it

A PiP button joins the OSD next to fullscreen, with P as its key. While floating, the main window's stage shows a placard (Chromium blanks the in-page element anyway), the full OSD keeps working — scrub, volume, sleep timer all still drive the same element — and closing the floating window brings the picture home. Phase 2 lets you leave the player entirely while the window floats.

5 · Implementation plan

  1. Session controller, DOM-free — src/renderer/src/player/pip.ts

    Follow the mse.ts pattern: all the logic worth testing in a module that never touches the DOM. A small state machine (idle → active → transferring → active) that consumes events — toggle, swapped, left, teardown — and returns commands — enter(slot), transfer(slot), exit, returnInline. The one sharp edge it encodes: leavepictureinpicture fires on the old element during a transfer, and must not be read as the user closing the window. The transferring state is that disambiguation — the same shape as wantsPlayRef distinguishing human pauses from mechanical ones. Also the ordering rule as an invariant: never exit before requesting during a swap, or the gesture-free transfer window (R2) closes.

  2. Player wiring — src/renderer/src/screens/Player.tsx

    • OSD button next to fullscreen + P in the key map + kbd-hints entry; pipActive local state mirrored from the controller.
    • Enter path inside the gesture handler: exitFullscreen() if needed, then request on activeVideo(). Catch NotAllowedError into the existing failure-card-free toast pattern rather than crashing the OSD.
    • The swap effect (the one that calls handle.promote() and re-asserts volume) asks the controller, and requests PiP on the promoted element when told to.
    • leavepictureinpicture listeners on both surfaces' elements, routed through the controller; a user-close returns the picture inline (and, phase 2, navigates back to the player screen).
    • Media Session: setActionHandler('nexttrack', skip) and MediaMetadata (show title, episode line, channel number) refreshed per episode. Overlay pause must clear wantsPlayRef so the sleep-while-paused rule sees a human pause.
    • Unmount cleanup: exitPictureInPicture() alongside the existing exit-fullscreen cleanup.
    • VideoSurface is untouched. Its handle already exposes the element; PiP is transport, and transport lives in the Player.

  3. Store flag — src/renderer/src/store.ts

    pipActive: boolean with setPipActive. Phase 1 needs it only for honesty in one place: leavePlayer() exits PiP before navigating. It becomes the load-bearing bit in phase 2.

  4. Phase 2: float over the whole app — src/renderer/src/App.tsx

    Today screen === 'player' is what mounts the Player, and unmounting kills the streams. Change the shell so the Player stays mounted while pipActive, hidden the same way the standby surface hides — opacity: 0, pointer-events: none, never display: none (the decoder-warmth rule in the stage comment applies to the whole stage here). Gate the Player's window-level key map on being the visible screen so Space in the Library doesn't pause the channel. Esc from the player with PiP active becomes “go browse” instead of “stop watching”; closing the floating window from anywhere returns screen to 'player'. Blackout still unmounts everything — the sleep timer wins over the float.

  5. Tests — tests/pip.test.ts, extend tests/handoff.test.ts

    • Controller: toggle→enter; swap while active→transfer targeting the promoted slot; left during transferring is swallowed; left while active returns inline; teardown from every state exits at most once.
    • Ordering invariant: no command sequence ever emits exit before transfer across a swap.
    • Handoff suite: promotion with PiP active leaves the standby unpromoted surface never targeted; sleep expiry with PiP active still blacks out.
    • jsdom has no PiP APIs — which is exactly why the controller is DOM-free; the spike (/tmp/pip-spike, reproducible from this plan) covers the real-Chromium facts the unit tests can't.

  6. Docs — docs/ui.md, docs/playback.md

    The interaction map from §4, the R2/R5 gesture rule (it reads like magic without the citation), and a pointer here.

6 · Edge cases & decisions

  • Why not Document PiP with the stage portaled in? It was the better architecture on paper — custom OSD in the float, no transfer dance — and it is simply not implemented in Electron 38 (R0). The controller seam keeps the option open; everything else in this plan survives that future swap.
  • Never exit-then-enter across a swap. R5 is why: with no live session there is no gesture-free request. The transfer (R2) is the only bridge, so the controller treats “session exists” as an invariant during handoffs.
  • The standby never floats. The controller only ever targets the active slot; the swap event carries the promoted slot id, so a race with a stale slot cannot pick the muted surface.
  • Overlay pause vs. the sleep timer. The expired-while-paused rule fires only on human pauses (wantsPlayRef). Chromium's overlay pause is a human pause arriving without our OSD — it must clear the ref via the pause event path, not bypass it.
  • Both PiP-close buttons look identical to us. ✕ and “back to tab” both fire leavepictureinpicture; Chromium doesn't say which. One rule for both: picture comes home, player screen shows it. No attempt to guess intent.
  • Failure card while floating: a dead stream in PiP shows a frozen frame with no explanation. On onStreamError/onError with PiP active, exit PiP so the existing Retry/Skip card is actually visible.
  • Auto-PiP on minimize — deliberately out. R5 forbids it from the renderer. The main process could fake a gesture (webContents.executeJavaScript(code, /* userGesture */ true) on the minimize event), and that hack is noted here so nobody rediscovers it — but shipping a synthetic-gesture workaround for a Chromium policy is the kind of cleverness this codebase has learned to distrust. Revisit only if real use asks for it.
  • Window geometry: Chromium sizes the float from the video's aspect and remembers the user's resize per origin. Nothing for us to persist.
  • Chromium paints its own caption. Found only by looking at the running app: while an element is floating, Chromium draws “Playing in picture-in-picture” inside the blanked element's box — outside the DOM, unstyleable, unsuppressable. The placard originally said exactly that too, so the screen stuttered. Shipped copy: “Keep watching while you browse”, plus the channel and episode — the things the browser's line does not say.
  • On Wayland the window cannot stay on top — and that is not ours to fix in the player. A Wayland client has no protocol to raise itself above other clients, so Chromium's always-on-top request is silently dropped and the floating window is one any other window can bury; with no titlebar there is not even a window menu to correct it by hand. The same build under XWayland gets _NET_WM_STATE_ABOVE, STAYS_ON_TOP and STICKY for free. Shipped as Settings → “Keep picture-in-picture above other windows” (Wayland only, default on), which relaunches the app with --ozone-platform=x11 — appendSwitch and ELECTRON_OZONE_PLATFORM_HINT are both too late, because Chromium picks its Ozone platform before the main script runs. (npm run dev is the exception: relaunching there kills the dev server, so scripts/dev.mjs passes the flag instead.)
  • …and a full-screen window still beats a pinned one, because KWin stacks an active full-screen window above the whole “keep above” layer. No client-side API reaches the layers that outrank it — _NET_WM_STATE_ABOVE is everything X11 offers a window about its own stacking. The only mechanism is a window rule, so on KDE the app writes one (main/kwin-rule.ts): Layer: Force → Overlay, matched on the title, since the PiP window carries no WM_CLASS and no window role. Idempotent, removed when the setting is switched off, and every other rule in kwinrulesrc preserved. Verified against a real full-screen game. See docs/ui.md.
  • Loudness, prewarm, sleep, scrub-by-URL: all unchanged — they act on streams and elements, and PiP moves pixels, not playback.
