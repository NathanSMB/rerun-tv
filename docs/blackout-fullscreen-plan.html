Blackout keeps fullscreen — fix plan

When the sleep timer expires while the Player is fullscreen, the screen goes black but the window drops back to windowed mode — chrome, taskbar and all. The blackout exists to emit nothing; a taskbar is a light source. This plan explains why it happens and how to keep the black screen fullscreen.

Status: implemented. All three changes are in, with two deviations from the draft — see §7. 497 tests pass; the KWin/Wayland pass in §6 is the one step left, and needs a real session.

1 · The symptom

Watching fullscreen with the sleep timer armed. The timer expires at an episode boundary (or via the panel's doze off now button). The picture is replaced by the blackout screen — correct — but the app simultaneously leaves fullscreen, so the desktop's panel and the window's titlebar come back. In a dark room, the "sleep" screen turns the lights on.

2 · Root cause

Fullscreen in Rerun TV is element fullscreen: F calls stageRef.current.requestFullscreen() on the Player's stage wrapper (src/renderer/src/screens/Player.tsx:793) — deliberately the wrapper, never a <video>, so episode handoffs can't take the fullscreen element with them (decision #1 in the Player's file header). The window is never put into fullscreen by the main process; the OS-level fullscreen you see is Chromium's side effect of element fullscreen.

The blackout, however, is a different screen, not a state of the Player:

  1. The timer expires and the boundary is reached — either the sleep check in advance() (store.ts:413) or sleepNow() (store.ts:548) — and both call goDark().
  2. goDark() releases the channel and sets screen: 'blackout' (store.ts:262).
  3. App.tsx renders screens exclusively: 'blackout' returns <Blackout /> alone (App.tsx:186–192), which unmounts the Player — and with it the stage <div> that is the current fullscreen element.
  4. Two things now drop fullscreen, either of which is sufficient:
    • Removing the fullscreen element from the DOM makes Chromium exit fullscreen automatically. This is spec behaviour, not a bug.
    • The Player's fullscreenchange effect cleanup calls document.exitFullscreen() unconditionally on unmount (Player.tsx:806–807) — "leaving the player must not strand the window in fullscreen". Correct for Esc-to-guide; wrong for going dark.

In one sentence: fullscreen belongs to a DOM element owned by the Player, and going to sleep destroys the Player — so fullscreen dies with it, by design of the Fullscreen API, before the blackout ever mounts.

3 · The fix — hand fullscreen to a custodian that survives the swap

Before the Player unmounts, transfer fullscreen from the stage to document.documentElement — an element that exists on every screen. When the stage is then removed, it is no longer the fullscreen element, so fullscreen survives the Player → Blackout swap with no flicker. The blackout renders at 100vh on a #000 background already, so it fills the fullscreen viewport untouched.

Why this is allowed without a click: Chromium requires a user gesture for a fresh requestFullscreen(), but permits re-targeting fullscreen to another element while the document already holds a fullscreen element — the same "session already exists" family of allowance the PiP work verified for requestPictureInPicture() transfers (docs/pip-plan.html §2). Step 0 below spike-verifies it in our Electron before building on it.

Change 1 — the handoff in goDark() src/renderer/src/store.ts

The store is compiled without the DOM library — it is the one renderer file the Node tests drive directly, and tsconfig.node.json enforces that by giving the project no lib: DOM at all. So the handoff reaches the document the same way the store already reaches the preload bridge: through globalThis, structurally typed, and simply absent under test.

type FullscreenDoc = {
  fullscreenElement: unknown
  documentElement: { requestFullscreen: () => Promise<void> }
}

// Re-target fullscreen to the document root — permitted without a gesture
// while a session exists — so the blackout inherits the same dark, chromeless
// screen the picture had.
async function handOffFullscreen(): Promise<void> {
  const doc = (globalThis as { document?: FullscreenDoc }).document
  if (!doc?.fullscreenElement) return
  await doc.documentElement.requestFullscreen().catch(() => undefined)
}

async function goDark(get, set): Promise<void> {
  // Before anything is torn down, so the handoff lands while the stage the
  // Player is holding fullscreen with is still in the document.
  await handOffFullscreen()
  // ...existing release calls, then set({ screen: 'blackout', ... })
}

On a rejection (or when the viewer was windowed) this is a no-op and behaviour degrades to exactly today's. Both sleep paths — the episode boundary and doze off now — run through goDark, so one change covers both.

Change 2 — guard the Player's cleanup src/renderer/src/screens/Player.tsx:806

return () => {
  document.removeEventListener('fullscreenchange', onChange)
  // Leaving the player must not strand the window in fullscreen — but only
  // when fullscreen is still ours. Going dark hands it to the document root
  // first, and that handoff must survive this unmount.
  if (document.fullscreenElement === stageRef.current) {
    void document.exitFullscreen().catch(() => undefined)
  }
}

The Esc-to-guide path is unchanged: there the stage is still the fullscreen element at cleanup time, so the guard passes and fullscreen exits as before.

Change 3 — the blackout's exit drops fullscreen src/renderer/src/screens/Blackout.tsx

const backToGuide = useCallback(() => {
  // The guide is a windowed screen with an app bar; a fullscreen guide is
  // not a state the app has. Exit before navigating (no-op when windowed).
  if (document.fullscreenElement) void document.exitFullscreen().catch(() => undefined)
  navigate('guide')
}, [navigate])

Esc semantics — corrected from the draft. The draft assumed Chromium exits fullscreen on Esc and still delivers the keydown. The Player's keyboard map says otherwise, and it was written against measured behaviour: the key is swallowed, which is exactly why its first Esc only un-fullscreens and a second is needed to leave. The blackout inherits the same two-step — first press leaves fullscreen, second returns to the guide. Enter and the button do both in one press, and the explicit exitFullscreen() above also makes a single Esc sufficient on any browser that does deliver the key. Deliberately not done: navigating on fullscreenchange. It would make one Esc enough everywhere, at the price of the compositor being able to throw the app into a bright guide any time something else takes fullscreen away.

4 · Cases considered

ScenarioBehaviour after the fix
Timer expires, Player fullscreen Blackout appears still fullscreen; screen stays black edge to edge.
Timer expires, Player windowed document.fullscreenElement is null → handoff no-ops; identical to today.
Timer expires while the picture floats in PiP Fullscreen is never active in that state (the two are mutually exclusive, Player.tsx:369–371) → handoff no-ops; PiP window closes as today.
Doze off now pressed while fullscreen Same path (sleepNow → goDark), same handoff.
Handoff rejected by Chromium Caught and ignored → today's behaviour (black but windowed). Never worse than the status quo.
Enter / click on the blackout Fullscreen exits and the guide appears windowed, in one gesture.
Esc on a fullscreen blackout Two presses — the browser takes the first to leave fullscreen. Same as the Player; see §3.
Esc-to-guide from the fullscreen Player Unchanged — the cleanup guard still matches the stage there.
OS display-sleep on the blackout Unchanged — the wake lock is already released with the channel; fullscreen does not hold one.

5 · Fallback, if the gesture-less handoff is refused

If the step-0 spike shows our Electron refusing the re-target, fall back to window fullscreen from the main process, which needs no gesture: an IPC call in goDark asks main for win.setFullScreen(true) after element fullscreen collapses, and the blackout's exit path calls win.setFullScreen(false). Downsides — it mixes the app's two fullscreen systems and may flash window chrome for a frame between element-fullscreen exit and window-fullscreen entry (worth checking on KWin/Wayland specifically). It is the reliable-but-uglier option, which is why it is the fallback and not the plan.

7 · What was built

Two deviations from the draft, both above: the store reaches the document through globalThis rather than importing DOM types (§3, change 1), and Esc on a fullscreen blackout is a two-step rather than one (§3, change 3).

Tests

The bug is not inside either component — it is in the seam between them — so it is pinned from both sides. Each was confirmed to fail with the corresponding half of the fix reverted; neither is a test that would pass anyway.

  • Store, in Node tests/handoff.test.ts — "going dark keeps fullscreen": the handoff is asked for, and asked for while the screen is still player, which is the ordering the whole fix rests on; nothing is requested for a windowed viewer; a refused re-target still goes dark, releases the channel and logs the episode; walking out to the guide asks for nothing. The document is a stand-in on globalThis, faked the way the preload bridge already is.
  • Both screens, mounted tests/renderer/blackout-fullscreen.test.tsx — the swap itself: fullscreen survives from the picture to the black screen (and to a paused expiry), a windowed viewer is left windowed, all three exits drop fullscreen on the way to the guide, and the Player still gives fullscreen up when it should — walking out, or handing the picture to a floating window.
  • Harness tests/renderer/harness.tsx — a fullscreen model alongside the existing media and PiP ones, carrying the two rules this feature turns on: a detached element reports as no fullscreen at all (which is what makes the original bug reachable from a test), and a fresh request needs a gesture while a re-target does not. Esc-in-fullscreen is modelled as swallowed, per §3. The blackout is now mounted by the harness shell — it is the one other screen whose behaviour is a consequence of the Player's teardown.
