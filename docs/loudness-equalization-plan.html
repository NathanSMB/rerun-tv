Loudness equalization

Episodes come from different sources mastered at very different levels, and within an episode action scenes swamp dialogue. This plan adds a single Loudness equalization toggle that fixes both — normalizing every episode to one target and evening out dynamics inside each one — by extending the existing ffmpeg audio filter chain.

The problem

Integrated loudness varies with where an episode came from. Web downloads tend to sit near modern streaming targets, DVD remuxes are mastered 5–8 LU quieter, and broadcast captures are all over the place. The result: the volume knob is wrong every time the schedule crosses a source boundary.

Inside a single episode the same thing happens over time: dialogue scenes sit 10–15 LU below the action peaks. Cross-episode gain alone can't fix that — it moves the whole curve up or down. The fix needs a time-varying component that lifts quiet passages and tames loud ones toward the target.

The approach: extend the one audio-encode point

All ffmpeg audio-arg construction already funnels through a single function — aacArgs() at src/main/stream/server.ts:608 — which builds the one -af chain (currently just the aformat channel-layout guard that Chromium's MSE AAC parser requires). Loudness processing slots into that same chain. Two rules keep it safe: the new filters are appended into the existing -af string (a second -af would silently replace the first), and aformat stays last so the channel-layout guarantee still holds at the encoder input.

One filter, loudnorm, covers both requirements. In its default dynamic mode it continuously measures loudness and adapts gain toward the target — so quiet DVD remuxes come up, hot broadcast rips come down (cross-episode), and soft dialogue is lifted while action peaks are held near the target (within-episode). Phase 1 ships exactly this:

-af loudnorm=I=-16:TP=-1.5:LRA=11:dual_mono=true:linear=false,aresample=48000,aformat=channel_layouts=mono|stereo|3.0|4.0|5.0|5.1|7.1

Dynamic loudnorm's one weakness is the first few seconds: it starts from an assumed level and converges as it measures — and since a seek respawns ffmpeg, that wobble is paid again on every scrub. Phase 2 removes it by measuring each episode once in the background and putting a fixed volume=<offset>dB pre-gain in front of loudnorm. The input then arrives already at target, so frame one is right and loudnorm's dynamic gain sits near unity doing only the within-episode work:

-af volume=6.80dB,loudnorm=I=-16:TP=-1.5:LRA=11:dual_mono=true:linear=false,aresample=48000,aformat=…

Not by handing the measurements to loudnorm as measured_I/measured_TP/…, which is what this plan originally proposed. Those options exist to enable linear mode — one scale factor applied to the whole file — which solves the across-episode half and abandons the within-episode half; and in dynamic mode ffmpeg ignores them entirely. Hence the explicit linear=false, and the pre-gain carried by volume instead.

Why the cost is low for this library

About 85% of the library is H.264 + AC3 — those episodes already take the remux path with an audio re-encode (AC3 isn't MSE-playable), so loudness EQ adds only a filter to an encode that is already running: near-zero marginal CPU. The table below covers every playback path.

Settings

One toggle in the existing Playback card in Settings.tsx, following the prewarmNext pattern end-to-end (type + default in src/shared/types.ts, generic settings.set IPC, Zustand setSetting(), Toggle row). Settings are read at request time (server.ts:33), so the toggle takes effect on the very next tune-in with no restart. A dynamic-range intensity select can follow in phase 3 if wanted.

  • DB migration for measured R128 values
  • Idle-time scan queue keyed off library scans

Risks

RiskMitigation
Prewarmed standby carries stale audio args → audible jump at episode handoff Release the pending job when the toggle changes (phase 1, store.ts cleanup above); active episode keeps its sound until the next natural boundary.
loudnorm outputs 192 kHz internally; AAC/MSE expects 48 kHz Explicit aresample=48000 in the chain, covered by arg tests.
Dynamic mode gain-pumping on hard transients LRA=11 is conservative, and the phase-2 pre-gain keeps loudnorm's dynamic gain near unity instead of holding several dB across the whole episode; phase 3 can trade loudnorm aggressiveness for a dedicated compressor.
Formerly copy/direct files now spend CPU on audio encode Audio-only AAC encode is cheap (≪ 1 core); applies only to the ~15% non-AC3 slice, only while the toggle is on.
Measuring the library is a full audio decode per file Only the audio stream is mapped, so the video is never decoded — seconds per episode, not minutes. It runs one file at a time on a single thread, waits while anything is playing or scanning, and the feature never blocks on it: an unmeasured episode simply plays with the phase-1 chain.
A file that will not decode stalls the measuring queue Failures are skipped and remembered for the session, so a pass never spins on one file; not persisted, so a temporary cause (an unmounted drive, a file mid-copy) is retried on the next launch.
