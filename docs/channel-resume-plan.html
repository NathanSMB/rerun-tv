What the user gets

Every channel remembers its own spot. Tune away to another channel, drop back to the guide, close the window, or lose the app to a crash — when you tune that channel in again, the same episode picks up where it left off (a crash costs at most the last 30 seconds). When an episode finishes normally, the channel advances as it does today and the remembered spot moves to the top of the next episode.

This deliberately reverses a documented design decision — docs/architecture.md:42 says "tuning in starts the next episode from the top" and lists mid-episode resume as out of scope (docs/architecture.md:204-215). The reversal is intentional (it is TODO item 2); the docs updates in step 7 make the new contract the documented one.

The one constraint that shapes the design

The scheduler commits at hand-out time, so resume must not pick.

pickNext (src/main/scheduler/scheduler.ts:408-425) runs saveShowState + setActiveArc + logAiring in one transaction the moment an episode is handed out — before a single frame plays. By the time the viewer leaves mid-episode, the sequential cursor already points at the next unit, the shuffle bag has been popped, a multi-part arc lock already points at the next part (scheduler.ts:291-313), and a play_log row with completed = 0 already exists (src/main/db/repositories/channels.ts:485-494).

A resume that re-tunes through pickNext would therefore double-spend a schedule step and hand back a different episode than the one saved. The resume path must return the saved episode directly, calling pickNext not at all and writing no second play_log row.

When state gets saved

Two write paths, one table. The main process writes the row at pick time — whenever an episode is handed out, the row is set to (episode, 0 s). The renderer then updates the position: every 30 seconds on an interval, and immediately on the events that matter (leaving the channel, tuning elsewhere, seeking, the window being hidden or closed). Because every save is a synchronous better-sqlite3 upsert completed inside the IPC handler, a save is durable the moment the handler returns — quitting needs no flush, no before-quit hook, and no renderer round-trip.

Data model

One new table, appended to MIGRATIONS in src/main/db/schema.ts (append-only per the file's header — this becomes the seventh entry). It mirrors the existing split that keeps progress out of configuration: channel_show_state is scheduling progress, this is playback progress. Keyed by channel, not episode — a channel resumes where it was, and the same episode can sit at different positions on two channels. A settings row was rejected as the wrong grain: this is per-channel state, not a user knob.

Repository functions (all SQL stays in src/main/db/repositories/): upsertPlaybackState, getPlaybackState, clearPlaybackState. The existing "reset progress" flow that clears channel_show_state should clear this row too — a reset channel starting mid-episode would be a surprise.

IPC surface

One new method, one extended type — the contract discipline in docs/architecture.md:120-129 and the type-level assertions in tests/renderer/bridge.ts:60-69 enforce that all three layers move together:

  • RerunApi (src/shared/ipc.ts) gains player.savePosition(channelId, episodeId, positionS): Promise<void>, plus its entry in the IPC.player channel map and the one-line bridge in src/preload/index.ts. No clearPosition over IPC — clearing is a main-process concern (pick-time overwrite, reset-progress).
  • NowPlaying (src/shared/types.ts:286-295) gains resumeAtS: number (0 for a fresh pick), which the renderer uses to seed the slot.
  • The handler for savePosition validates that (channelId, episodeId) still matches the channel's current row before writing, so a stale flush from a torn-down player can't clobber a newer pick.

Edge cases, decided

ScenarioBehavior
Crash right after an episode advancesNo position was autosaved yet for the new episode — but main wrote (new episode, 0 s) at pick time, so reopening resumes the correct episode from the top. No schedule step is double-spent and nothing is skipped.
Saved position is in the final secondsresumeAtS is clamped to duration − 5; playback resumes, plays the tail, and the normal advance() path (store.ts:617-672) moves on. No special "almost done" logic.
Saved episode deleted from the libraryStaleness check fails → fresh-pick branch; the row is overwritten by the new pick. The FK cascade covers the DB-level cleanup.
Crash during the prewarm windowStandby reservations live in an in-memory WeakMap (scheduler.ts:457-466) and vanish by design; the saved row still points at the current episode, which is the correct recovery.
Window backgrounded (timer throttling)The sleep-timer precedent (store.ts:258-266) warns that intervals drift when backgrounded — hence the visibilitychange flush at the moment of hiding, which is exactly when position stops changing for a paused/hidden player. With video still playing (PiP), timeupdate-driven state keeps the interval's reads fresh.
Resume + multi-part arcResume never touches active_part_index; leaving mid-part-2 and returning resumes part 2, and the lock still points at part 3 for the next natural advance — exactly the committed state.
Sleep timer setting precedentsleepTimerDefaultMin's comment (types.ts:496-499) says an armed countdown must not survive a restart. Unchanged — resume restores position, never timer state.
Position ≈ 0 (left almost immediately)Still resume the saved episode (from ~0). Falling through to pickNext would double-spend; there is no threshold below which resume becomes a re-pick.

Implementation steps

  1. Migration + repository. Append the channel_playback_state migration in src/main/db/schema.ts; add src/main/db/repositories/playback-state.ts with upsertPlaybackState / getPlaybackState / clearPlaybackState; hook clearPlaybackState into the existing reset-progress flow.
  2. Shared contract. Add resumeAtS to NowPlaying (src/shared/types.ts); add player.savePosition to RerunApi + IPC.player (src/shared/ipc.ts) and the preload bridge (src/preload/index.ts). Typecheck failures walk you to every site that must change.
  3. Resume decision in main. New services/ function (e.g. resolveTuneIn(db, channelId)) implementing the resume/fresh-pick branch; the player.tune handler (src/main/ipc/handlers.ts:328-337) calls it and threads resumeAtS into toNowPlaying → urlFor(episodeId, resumeAtS, channelId) at handlers.ts:131-133. Add the pick-time upsert wherever pickNext hands out an episode (tune + advance paths), and the savePosition handler with its stale-flush guard.
  4. Renderer seeding. On tune, build the initial slot with slotFor(playing, playing.resumeAtS, playing.streamUrl) for piped modes; for direct mode set currentTime after loadedmetadata — the same two-branch shape as performSeek (Player.tsx:609-637). Note the in-render videoTime reset at Player.tsx:173-179 already handles the episode-change case.
  5. Renderer autosave. New Player.tsx effect: 30 s setInterval writing offset + videoTime (teardown-safe, per the FfmpegGate.tsx:96-106 template); flush calls in leavePlayer / tune / goDark (before each release), in commitSeek, and on visibilitychange-hidden / pagehide.
  6. Tests. Scheduler-side: resume leaves cursor / shuffle bag / active_part_index / play_log untouched; stale-row fallback; pick-time upsert (extend tests/scheduler.test.ts and tests/handoff.test.ts). Renderer-side: interval + flush behavior and slot seeding in tests/renderer/player-decisions.test.tsx, with the new bridge method stubbed in tests/renderer/bridge.ts / harness.tsx.
  7. Docs. Update docs/architecture.md (channel model at :42; strike mid-episode resume from out-of-scope at :204-215), docs/data-model.md (new table beside channel_show_state), docs/playback.md (resume + coarse-seek note), and docs/ui.md's "Player" section, which handlers.ts:131-133 cites for the old from-the-top rule.

Explicitly out of scope

Cross-episode "continue watching" lists, per-show resume (this is per-channel), frame-accurate seeking on piped paths, and any persistence of the sleep timer. The play_log semantics (docs/playback.md:177-184: one row per viewing, completed flipped only by markLastAiringCompleted, channels.ts:500-514) are deliberately unchanged — resume neither adds rows nor flips flags.
