Rerun TV

A Linux desktop app that turns a local media library into lean-back TV channels: you build the lineup, the channel decides what's on. This document is the MVP plan — locked decisions, system architecture, data model, the scheduling algorithm, playback pipeline, and build order.

2 · System architecture

Everything lives in one Electron app. The main process owns the library, the database, the scheduler, and a loopback HTTP stream server that fronts ffmpeg; the renderer is a plain web UI whose <video> element points at that server. The renderer never touches the filesystem.

Why a loopback HTTP server instead of file://?

  • One URL shape for all three playback paths — the <video> element never knows whether it's getting a range-served file, a live remux, or a transcode.
  • ffmpeg can pipe fragmented MP4 straight into the HTTP response; no temp files.
  • Post-MVP it's already the seam for casting to another device on the LAN.

3 · Library: scanning & parsing

The user adds one or more root folders in Settings. The scanner walks them, parses filenames, probes each file with ffprobe, and writes the result to SQLite. Scanning is incremental — files are keyed by path + mtime + size, so a rescan only probes what changed.

Filename parsing

  • Show name comes from the top-level folder; season/episode from the filename: S01E03, 1x03, and S01E03-E04 (double episodes) are the MVP grammar.
  • Episode titles are whatever trails the episode code, cleaned of separators; no network metadata lookups in the MVP.
  • Files that don't parse land in an Unmatched bucket in the Library screen, where they can be assigned to a show/season/episode by hand.

Multipart detection

  • Auto-grouping heuristic: consecutive episodes whose titles match Part N / (N) / Pt. N with the same stem (e.g. The Gathering — Part 1 / Part 2) become an arc.
  • The heuristic is only a head start — the Library UI lets you group or ungroup any run of consecutive episodes into an arc, which is the source of truth (part_groups table).

ffprobe at scan time

Each file is probed once and its duration, container, and codec pair are stored. This is what makes the playback decision (§6) instant at tune-in, and durations are what a future simulated-live schedule will need.

4 · Data model

Eight tables. Channel state is deliberately separated from channel definition: the lineup (channel_shows) is configuration, while cursors and shuffle bags (channel_show_state) are progress that can be reset without touching the lineup.

The key abstraction: the playable unit. A unit is either a standalone episode or an entire multipart arc. Cursors, shuffle bags, and the lottery all operate on units, never raw episodes. This one decision is what makes arcs uninterruptible and exactly as likely to air as any single episode — it falls out of the model instead of being special-cased.

5 · The scheduler — what plays next

When a channel needs its next episode (tune-in, auto-advance, or skip), the scheduler runs a two-stage pick over the channel's lineup. Arc playback preempts everything: once an arc starts, nothing interrupts it until the final part ends.

function nextEpisode(channel):
  # 1 · An in-progress arc always wins — arcs are never interrupted
  if channel.active_group_id:
      return nextPart(channel)            # clears arc state after the last part

  # 2 · Pick a show (weighted; weights are per-show sliders in the editor)
  show = weightedRandom(channel.shows, by=weight)

  # 3 · Pick a unit within that show, by the show's mode
  if show.mode == sequential:
      unit = show.units[state.cursor]; state.cursor += 1  # wraps to 0 at the end
  else:  # shuffle — a dealt bag, so nothing repeats until all units have aired
      if state.shuffle_bag.isEmpty():
          state.shuffle_bag = shuffled(show.units, avoidFirst=lastAired)
      unit = state.shuffle_bag.pop()

  # 4 · Arcs enter as one unit and lock the channel until they finish
  if unit.isArc: channel.active_group_id = unit.id

  log(channel, unit.firstEpisode); return unit.firstEpisode
  • Sequential shows keep a cursor over their unit list in season/episode order — after S01E03 airs, the next pick of that show is S01E04. The cursor wraps back to the pilot after the finale.
  • Shuffle shows deal from a bag: every unit airs once before any repeats, and a freshly refilled bag never leads with the unit that just aired.
  • Skip during an arc advances to the arc's next part (the arc still completes); skip otherwise triggers a fresh pick. Both are instant because the decision needs no probing.

Why the lottery is over units, not episodes

If shuffle drew raw episodes, a three-part arc would hold three tickets — it would start almost three times as often as any standalone episode (and could start at Part 2). Drawing units gives the whole arc exactly one ticket.

6 · Playback pipeline

Electron's Chromium plays H.264/AAC natively, so the stream server picks the cheapest path that yields a playable stream. The decision uses codec data already in the database — nothing is probed at tune-in.

  • Remux starts in milliseconds — stream copy is I/O-bound, no encoding. This is the expected path for a typical MKV library where the codecs are already H.264/AAC.
  • Transcode is the fallback, sized for one stream at a time (-preset veryfast, CPU-only in the MVP; VAAPI hardware encode is a post-MVP flag).
  • Seeking on piped streams restarts ffmpeg at -ss; the player translates timeline scrubs into a new stream URL with ?t=. Direct-play files seek natively via range requests.
  • The supervisor kills the previous ffmpeg job the moment a channel changes or skips — never more than one job per channel.

7 · Player behavior

  • Play / pause, volume up / down + mute (persisted across sessions), skip (next scheduler pick; next part if inside an arc), and a seek bar for the current episode.
  • Fullscreen toggle that survives transitions: fullscreen is requested on a wrapper element that contains the <video> and OSD — episode changes swap the video src inside it, so the fullscreen element never exits. Auto-advance on ended fires the scheduler, briefly shows the channel banner, and plays on.
  • OSD: controls and a channel banner (channel number, show, episode code/title) appear on mouse move or key press, fade after ~3s of idle. Keyboard map: Space play/pause, ↑/↓ volume, → skip, F fullscreen, Esc back to guide.
  • Resume rule (MVP): tuning back into a channel starts the next scheduled episode from its beginning; a partially-watched episode is logged as incomplete. (Mid-episode resume and simulated-live join are post-MVP.)

9 · Build order

Seven milestones, sequenced so there's a runnable app from milestone 1 and something genuinely usable (scan → tune → watch) by the end of milestone 4. The scheduler lands last among the core features because the player can loop a single show's episodes in order until then.

10 · Risks & mitigations

RiskMitigation
Seek latency on transcoded streamsKeyframe-aligned -ss before input (fast seek); accept coarse seeks in MVP. Most content direct-plays or remuxes, where seeking is native.
Filename chaos in real librariesThe Unmatched bucket + manual assignment means a bad parse never blocks a show from airing; parser grammar can grow case by case.
Transition gap between episodesPre-resolve the next unit and warm the next stream URL while the current episode is in its last 30s; the channel banner covers the handoff moment.
Electron codec driftCodec support is asserted at startup against a tiny embedded test asset; anything unplayable simply routes to the transcode path.
Scheduler state corruption (crash mid-arc)All state transitions are single SQLite transactions; an orphaned active arc is validated (and cleared if stale) at channel tune-in.

11 · Explicitly out of scope (post-MVP)

  • Simulated live schedules — a per-channel virtual clock so tuning in drops you mid-episode. The duration data and play log already support it.
  • Interstitials — bumpers/commercials from a clips folder between episodes. (This is the fun one.)
  • External metadata (TVDB/TMDB artwork & titles), movies as channel filler, LAN/TV-browser access, hardware (VAAPI) transcoding, multi-user profiles, mid-episode resume.
