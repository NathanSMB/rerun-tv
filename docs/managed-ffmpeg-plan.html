Rerun TV · Implementation plan

Managed FFmpeg

Let Rerun TV download and own a private copy of FFmpeg — first-launch gate when none exists, a version tracker with update checks in Settings, and every spawn routed to the managed binary when one is installed. Never added to PATH; never bundled with the app.

01Why this shape

Today the app resolves FFmpeg once per need through a single function, resolveFfmpeg() in src/main/stream/ffmpeg.ts, with precedence env override → PATH → bundled dirs. There is no bundled binary in real builds (no extraResources), so in practice it is "system or nothing" — and docs/architecture.md deliberately promises never to bundle one, which keeps the app clear of the GPL-distribution question.

A managed download keeps that promise: the app never distributes FFmpeg, it fetches an official upstream build at the user's request into the app's own data directory. That directory is private to Rerun TV (~/.local/share/rerun-tv/ffmpeg/), never touches PATH, and slots into the existing resolver as a new precedence tier.

Goals

  • First-launch modal when no valid FFmpeg exists: one-click download, or a link to install it yourself; auto-dismisses the moment a valid binary appears.
  • Settings → System: show the active FFmpeg (source, version, path); download a managed copy; check for and install updates; remove it.
  • All FFmpeg/ffprobe calls prefer the managed copy over the system one when both exist.

Non-goals

  • Bundling FFmpeg in the installer, or adding anything to the user's PATH.
  • Auto-downloading without consent, or background auto-updates (update checks are user-initiated).
  • A "prefer system over managed" toggle — deliberate simplification; removing the managed copy is the toggle. Easy to add later if wanted.

02Resolver: one new tier

The whole routing requirement collapses into one edit, because every consumer already funnels through resolveFfmpeg().

Concrete edits
  • ffmpeg.ts: add "managed" to the source union; insert a findManaged() step reading <dataDir>/ffmpeg/managed.json (validated with the existing isExecutable() + readVersion()). Keep the module-level cache; the install flow calls the existing resetFfmpegCache() when it finishes.
  • index.ts: pass Scanner and LoudnessScanner a getter (() => resolveFfmpeg().ffprobePath-style) instead of a captured string; the classes call it per operation. server.ts and handlers.ts already re-resolve per use and need no change.
  • No AppSettings key is needed at all — managed state lives in managed.json inside the managed dir, so the setSetting() whitelist in db/repositories/settings.ts is untouched.

03Download & install pipeline

A new main-process module, src/main/services/ffmpeg-manager.ts — the app's first outbound HTTP client. Modeled on the existing long-running-job patterns (scanner.ts progress broadcasts, loudness.ts AbortSignal cancellation).

On-disk layout

~/.local/share/rerun-tv/ffmpeg/          # join(dataDir(), "ffmpeg") — same shape as backupsDir()
├── managed.json                          # { version, urls, sha256, installedAt, platform, arch }
├── versions/
│   └── n7.1-latest/                      # one dir per installed version
│       ├── ffmpeg(.exe)
│       └── ffprobe(.exe)
└── .staging-<uuid>/                      # transient; deleted on completion, failure, or next boot
  • No symlinks. managed.json is the pointer (its version names the active dir under versions/). Symlinks need care on Windows; a JSON pointer works identically everywhere and is already the resolver's read path.
  • Updates are side-by-side. A new version installs into its own dir, then the pointer flips. FFmpeg processes already spawned from the old dir keep their open file handles; stale versions/ dirs are garbage-collected at next boot (alongside leftover .staging-*), so an update never yanks a binary out from under an in-flight stream.
  • Never on PATH — nothing outside the app reads this directory, and the resolver only consults it explicitly.

Where the binaries come from

PlatformSource (official static builds)ArtifactNotes

The manifest indirection: the app never scrapes those sites at runtime. A small ffmpeg-manifest.json lives in the NathanSMB/rerun-tv repo (fetched raw from GitHub over HTTPS) pinning exact download URLs and sha256 checksums per platform/arch, vetted by you when you bump it — optionally automated later by a CI job that watches upstream releases. A snapshot of the manifest is baked into the app as a fallback so a first install works even if the raw fetch fails. "Check for updates" = fetch manifest, compare its version to managed.json. This means an FFmpeg update never requires an app release, but users only ever download bytes whose hash the repo has signed off on.

Extraction without new dependencies: spawn the system tar — GNU tar on Linux handles .tar.xz, bsdtar ships with macOS and with Windows 10+ (tar.exe reads zip archives too). One guarded code path per archive kind; if tar is somehow absent, the error message routes the user to the manual-install link. (Fallback option if this proves flaky on Windows: PowerShell Expand-Archive, or a tiny yauzl dep — decision deferred until Phase 2 touches a real Windows runner.)

04First-launch gate

Rendered by a new FfmpegGate.tsx as a true modal overlay (scrim + centered dialog) mounted in App.tsx whenever system info reports source: "missing". The focus trap, Escape handling, and role="dialog" aria-modal pattern lift straight from SleepPanel.tsx — the only existing dialog — with new full-screen scrim CSS.

Behavior details
  • When it shows: the store's existing init() already fetches SystemInfo; the gate mounts when ffmpeg.source === "missing". It renders over the app shell (not replacing it) so boot continues normally behind it — consistent with the existing design note in App.tsx that errors shouldn't take the window, while still honoring "modal popup" for this genuinely blocking prerequisite.
  • "Install it myself" calls shell.openExternal("https://ffmpeg.org/download.html") via the existing IPC pattern, and flips the gate into the watching state.
  • Re-checking is a cheap main-process call: resetFfmpegCache() + resolveFfmpeg() + readVersion(). Triggered by window focus, a 5-second interval while the gate is visible, the [Check again] button, and install completion. On success the getter-seam consumers (Scanner, LoudnessScanner) start working on their next operation; the boot-time codec/hwaccel probes re-run via the same fire-and-forget pattern.
  • "Valid" means executable + version parses; the codec smoke test runs after, in the background, surfacing in Settings like today rather than blocking the gate.

05Settings integration

Extends the existing FFmpeg row in the System section of Settings.tsx (currently a read-only status line) into a small card. Reuses the section's own helpers: run() for busy-locking buttons, StatusDot, and the rail status logic.

  • The version tracker line always shows source badge · version · path for the active binary, plus the managed install's version when one exists but is shadowed by the env override.
  • Download/update progress renders inline in the card (same progress event the gate consumes); the rail's status dot goes "pending" during an install.
  • "Remove managed version" deletes the managed dir and re-resolves — the app falls back to the system binary, or the gate reappears if there is none. Confirmation runs through the HandlerContext dialog seam (not a bare dialog.showMessageBox) so handlers.test.ts stays green.
  • The renderer store gains the missing refreshSystem() action (system info is currently fetched only once in init()) plus a subscription to the progress event.

Corrupt or tampered download ✓Handled HTTPS + sha256 pinned in the repo-controlled manifest, verified before extraction; smoke test before activation; staging dir never becomes active on any failure.
Disk cost (~90–130 MB per platform archive + extracted) ✓Accepted User-initiated download with size shown up front; archive deleted after extraction; only one stale version survives until next boot.

08Test plan

  • Resolver precedence (Vitest, node env): fake executable stubs on a temp dir — the shebang-stub trick tests/stream-jobs.test.ts already uses — asserting env > managed > PATH > bundled > missing, plus cache-reset behavior.
  • ffmpeg-manager: pipeline against a local fixture archive and a mocked net (the Electron stub in tests/helpers/electron.ts grows a net.request shim): happy path, bad checksum, cancel mid-download, extraction failure — each asserting staging cleanup and that managed.json only appears on full success. Progress events observed via the stub's sentEvents.
  • Handlers: new channels registered once, readable error rewrap, dialog routed through the HandlerContext seam (the stub throws on direct dialog.* — by design).
  • Renderer (happy-dom + makeBridge): gate renders on source:"missing", download button drives progress states, gate unmounts when a re-check returns valid; Settings card per source state, update-check flows. Template: tests/renderer/settings-hwaccel.test.tsx. makeBridge derives its roll-call from the IPC map, so the new methods can't be silently unmocked.
  • CI: the manager suite must pass on all three OS runners (extraction is the platform-sensitive part); keep RERUN_REQUIRE_FFMPEG semantics — managed-download tests never hit the network, fixtures only.
  • Docs: update docs/architecture.md's "never bundles ffmpeg" paragraph to state the new stance precisely: still never bundled or distributed; optionally downloaded from upstream at the user's request.

09Decisions taken (flag if you disagree)

  • Managed beats system PATH whenever installed (the spec's routing rule); env vars stay above both as the dev escape hatch. No preference toggle in v1.
  • Gate is non-dismissible ("FFmpeg is required") but overlays a live app shell rather than replacing it, and self-dismisses via focus/poll re-check the moment any valid install appears.
  • Repo-hosted pinned manifest over live upstream-API queries: updates without app releases, but every byte checksum-vetted by the repo. In-app fallback snapshot for resilience.
  • GPL builds (not LGPL) from BtbN — the library is 85% H.264+AC3 and the streamer needs libx264; downloading at user request keeps the no-distribution stance intact.
  • No new dependencies for v1: Electron net (proxy-aware) + node:crypto + system tar. Revisit only if Windows extraction misbehaves on CI.
