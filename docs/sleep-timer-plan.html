Sleep timer

Implementation plan for Rerun TV — a countdown that lets the current playable unit (episode or multi-part arc) finish, then leaves the channel for a black screen whose only exit reveals itself on mouse movement.

Why this is a renderer-only feature

The scheduler already models “episode or arc” as one abstraction — PlayableUnit (src/shared/types.ts:155). Cursors, shuffle bags, and the lottery all pick units, and the arc lock (src/main/scheduler/scheduler.ts:249-267) guarantees an in-progress arc always wins the next pick. Crucially, the renderer already receives the unit-boundary signal on every episode: NowPlaying.arc is { title, partIndex, partCount } | null (src/shared/types.ts:284). So the whole predicate the sleep timer needs is:

const endsUnit = nowPlaying.arc === null || nowPlaying.arc.partIndex >= nowPlaying.arc.partCount

A standalone episode has arc === null (single-episode part groups too — the scheduler only locks when partCount > 1). Mid-arc, partIndex < partCount. Everything else the exit needs — player.reportEnded and player.release — already exists for leavePlayer().

What the viewer experiences

Two scenarios, both with a 30-minute timer armed at 0:00 over ~22-minute episodes. Blue is normal playback; orange is the grace period after expiry — the timer has fired but the unit gets to finish; the third color is the blackout screen.

The decision point

Everything funnels through one branch in store.advance() — already the single serialized path every episode-end takes. The check happens after reportEnded so the finished episode is logged as completed (unlike leavePlayer(), which reports completed: false).

The prewarm wrinkle — act 30 seconds early

prewarmNext is not a peek: it commits a schedule step (handlers.ts:247). If the timer has expired and the current episode ends its unit, the T−30s prewarm effect (Player.tsx:400-405) must be skipped — otherwise we commit an episode nobody will watch and have to walk it back. The blackout screen

A new Blackout.tsx screen, special-cased in App.tsx beside the Player (full window, no AppBar, no scroll container). It reuses the exact reveal machinery the Player OSD already has — reveal() + an idle-timeout effect (Player.tsx:358-379) and cursor: none when idle (Player.css:23-25). One button, hidden until the mouse moves, fading back out after a few idle seconds. Esc and Enter also return to the guide, so the exit is never mouse-only.

Try it — this mock implements the intended behavior (move your mouse inside, then hold still):

By design the screen is truly black when idle: the channel is fully released (ffmpeg encoders stopped via player.release), no wake locks are held — the app has no powerSaveBlocker — so the OS display-sleep policy can take over. That’s the point of a sleep timer.

Effort & sequencing

Build order

  1. Store first — sleep slice + the advance() branch. This is the whole feature’s correctness core and is exercisable before any UI exists (arm via devtools).
  2. Blackout screen + routing — so the branch has somewhere to land.
  3. Player UI — arm button, countdown chip, prewarm guard, keyboard shortcut.
  4. Settings — persisted default duration.
  5. Hardening — the edge cases below, plus a manual soak pass with a dev-only short preset.

Edge cases & decisions

SituationPlan
Timer expires while pausedRecommend: black out immediately. Nothing is “finishing,” and a paused player at expiry almost certainly means the viewer is asleep. (Alternative — wait for resume — deferred unless it feels wrong in practice.)
Expiry inside the last 30 s (prewarm already committed)Release pendingNext at the boundary; accept the incomplete play-log row — identical to the documented leavePlayer tradeoff.
User presses skip after expirySame branch, since skip funnels through advance(false): mid-arc it continues the arc; on a unit-final episode it ends the unit → blackout. A viewer who wants to keep watching cancels the timer.
User tunes to another channel while armedThe deadline is wall-clock and lives in the store, so it persists across tune() and applies to whatever unit is playing when it passes.
Timer expires on the guide/settings screenNo-op: quietly disarm. There is nothing to wind down, and blacking out a browsing user would be hostile.
Cancel during the grace periodReturn to normal playback; if inside the T−30s window, run the suppressed prewarm immediately so the handoff stays gapless.
A long arc defers sleep by an hour+Accept for v1 — it’s the requested behavior. The OSD chip makes it visible (“sleeps after Part 3/3”). Revisit a hard cap only if it annoys in practice.
Background-tab timer throttlingNon-issue by construction: expiry is a wall-clock comparison at the decision points (prewarm effect, advance, pause), not an accumulated countdown.

Test plan

  • Standalone episode: arm a dev-short timer, expire mid-episode → plays to the end, blackout, and no next pick was committed (check the schedule cursor didn’t move).
  • Mid-arc expiry → remaining parts play via the arc lock; blackout only after the final part; activeGroupId cleared.
  • Expiry inside the T−30s window → committed pendingNext released; no orphaned encoder (verify via the stream server’s release logs).
  • Cancel during grace → playback continues; prewarm re-fires if within the window; next handoff still gapless.
  • Skip after expiry on a unit-final episode → blackout; skip mid-arc → arc continues.
  • Blackout screen: button hidden on entry, revealed on mousemove, fades after idle, cursor hides; click / Esc / Enter all reach the guide with the timer off.
  • Expiry while paused → behaves per the decision above.
  • Tune to a new channel while armed → timer carries over and fires against the new channel’s unit.
  • Fullscreen: blackout keeps fullscreen; returning to the guide restores the normal chrome.
  • Reduced-motion: reveal/fade transitions respect prefers-reduced-motion like the existing OSD.

As built

Shipped as planned, with the store branch, the blackout screen, and the arc behavior all landing where this document put them. Four things are worth recording because they differ from the plan, and two of them are bugs the plan’s reasoning did not anticipate.

ChangeWhy
The paused branch keys on viewer intent, not on pausedTwo bugs, both found by running the real app, neither reachable from a unit test. Chromium fires pause immediately before ended (same millisecond, ended already true), so keying on paused raced the normal end-of-episode path and logged fully-watched episodes as completed: false — the flag a shuffle bag reads. And a promoted standby is paused for an instant, so a timer that expired mid-arc stopped at the handoff into part 2 — exactly what the unit boundary exists to prevent. The Player now keys on wantsPlayRef, cleared only in togglePlay, where a human actually asked.
The prewarm guard lives in both the Player effect and store.prewarm()The plan put it only in the effect. The serialization queue can hand the store a state the effect never saw, so the store re-checks authoritatively; the effect still skips the call to avoid the round trip, and deliberately leaves prewarmedAfterRef unset so cancelling re-fires it in time.
Blackout does not keep fullscreen (since reversed)The Player’s existing unmount cleanup exits fullscreen deliberately (“leaving the player must not strand the window in fullscreen”). Fighting that for a screen that is black either way wasn’t worth it. Reversed later: the dropped fullscreen hands a dark room its window chrome and taskbar back, which defeats the screen’s purpose. The blackout now inherits fullscreen via a handoff to the document root — see blackout-fullscreen-plan.html.
