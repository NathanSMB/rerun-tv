What this setting actually touches

The playback decision is made at scan time and stored per episode (shared/playback.ts): direct files are range-served off disk and remux files get a video byte-copy — neither ever runs a video encoder, so hardware acceleration is irrelevant to them. Everything here concerns the transcode path in transcodeArgs (src/main/stream/server.ts:698), which since the library grew now carries 476 of 878 episodes: 293 HEVC (x265 web rips, 143 of them 10-bit 1080p) and 183 MPEG-4 ASP (DVD-era XviD). Hardware mode accelerates both halves of that pipeline — the decode via -hwaccel, the encode via h264_vaapi / h264_nvenc. Audio is untouched: AAC encoding is always software (no hardware audio encoder exists), and the fMP4 mux is unchanged.

The probe finding that shaped the design

VAAPI device selection is not guessable. On this machine /dev/dri/renderD128 is the RTX 5080 — its VAAPI driver exposes no H.264 encode entrypoint and fails with No usable encoding entrypoint found for profile VAProfileH264High. The working device is the AMD iGPU on renderD129. So the capability probe must enumerate render nodes and test-encode on each, not default to renderD128 the way most VAAPI examples do.

/dev/dri/renderD128 — NVIDIA RTX 5080 VAAPI H.264 encode entrypoint missing (nvidia driver exposes decode only). h264_vaapi fails · h264_nvenc OK via CUDA
/dev/dri/renderD129 — AMD Granite Ridge iGPU Full VAAPI encode path verified, including the 10-bit→NV12 fold and software-decode fallback for XviD. h264_vaapi OK — the probe's pick

Design — one dropdown, three arg recipes

The setting becomes hardwareAccel: 'software' | 'vaapi' | 'nvenc' (replacing hardwareEncode: boolean, which shipped disabled and was never read). Only two segments of the ffmpeg command line swap per backend — the decode prefix ahead of -i and the video branch — while the seek, stream maps, audio chain, and fMP4 mux stay byte-identical. That containment is the whole safety argument: the software row below is exactly today's command.

shared — identical across backends swapped per backend
Software
no decode prefix -ss <t> -i file -map 0:v:0 -map 0:a:0? -map_chapters -1 -c:v libx264 -preset <p> -crf <q> -pix_fmt yuv420p -c:a aac -b:a <br> -af <loudness,aformat> -movflags frag… -f mp4 pipe:1
VAAPI
-init_hw_device vaapi=va:<node> -hwaccel vaapi -hwaccel_output_format vaapi -filter_hw_device va -ss <t> -i file -map … -vf format=nv12|vaapi,hwupload,scale_vaapi=format=nv12 -c:v h264_vaapi -rc_mode CQP -qp <q+3> -c:a aac … -movflags … pipe:1
NVENC
-hwaccel cuda -ss <t> -i file -map … -c:v h264_nvenc -preset <p2–p6> -rc vbr -cq <q> -b:v 0 -pix_fmt yuv420p -c:a aac … -movflags … pipe:1

Two deliberate robustness choices, both verified against real files:

  • VAAPI filter chain tolerates decode fallback. format=nv12|vaapi,hwupload accepts frames whether the decoder produced VAAPI surfaces or fell back to software (MPEG-4 ASP has no VAAPI decoder — the 183 XviD episodes decode on CPU and still hardware-encode; verified at 38.5×). scale_vaapi=format=nv12 folds 10-bit P010 surfaces to 8-bit, which h264_vaapi requires.
  • NVENC takes frames from system memory. Using plain -hwaccel cuda (no -hwaccel_output_format cuda) means decoded frames land in RAM, so any codec NVDEC can't decode falls back to software decode transparently and the encode still works (XviD verified at 57.7×). The cost is the copy + format conversion — the 321% CPU above — which is still 5× cheaper than software.

What the calibration pass found

VAAPI's first cut mapped the default tier to QP 24, on the theory that a fixed-function encoder wants a few points of slack. Measured against three scenes from a 10-bit HEVC source — picked by sweeping the episode for luma and motion, not by eye — that ran 45–59% below libx264's bitrate for the same tier, and the missing bits showed up as visible blocking in shadow. QP 20 lands within ~10% and restores the detail; the whole column shifted four points to keep the tiers ordered. NVENC needed no correction — it erred generous (+39%) and was clean by eye.

Phase 1 — The setting, the arg builders, the dropdown

PHASE 1Effort: small (about half a day) · independently shippable · software path byte-identical

Everything needed for the feature to work when the user picks a backend that actually exists on their machine. A new stream/hwaccel.ts module owns the three recipes; transcodeArgs composes them; the Settings screen swaps the dead toggle for a live dropdown. No probing yet — Phase 2's job — so the dropdown trusts the user, and Phase 3's fallback is the safety net behind that trust.

Phase 2 — Probe at startup, tell the truth in Settings

PHASE 2Effort: small-medium (half a day to a day) · same pattern as the existing checkCodecs assertion

The app already proves at startup that ffmpeg can produce the one stream shape Chromium needs (checkCodecs, a 0.2-second lavfi encode). This phase extends that idea per backend: a tiny test encode through h264_nvenc, and through h264_vaapi on each /dev/dri/renderD* node until one passes — the renderD128/129 finding above is exactly why enumeration, not convention, picks the device. Results surface in SystemInfo and the Settings screen, and the stream server consults them so a selected-but-absent backend routes to software without ever spawning a doomed job.

src/main/stream/hwaccel.tsprobeHardwareAccel(ffmpegPath): for NVENC one lavfi test encode; for VAAPI, enumerate render nodes (injectable lister for tests), test-encode on each, record the first passing device. RERUN_VAAPI_DEVICE env override skips enumeration — same escape-hatch convention as RERUN_FFMPEG_PATH. 15 s timeout per candidate, children killed on settle, result cached for the process lifetime.
src/shared/types.tsSystemInfo gains hwAccel: { nvenc: 'ok' | 'failed' | 'pending'; vaapi: 'ok' | 'failed' | 'pending'; vaapiDevice: string | null }.

Acceptance criteria

  • On this machine the probe answers: NVENC ok, VAAPI ok on /dev/dri/renderD129 (never 128).
  • Startup latency unchanged — probe runs after the window is up, like checkCodecs.
  • Selecting a failed backend plays via software with a single logged warning, not a broken stream.
  • Settings shows both backends' verdicts within a few seconds of launch.

Risks & notes

  • A probe passing on lavfi 64×64 doesn't guarantee every profile/resolution — real-file failures exist (driver quirks, session limits). That residue is Phase 3's job.
  • Render nodes can appear/disappear (eGPU, driver reload). The probe is per-process; a restart re-answers. Good enough for a living-room app.
  • NVENC concurrent-session cap on consumer GPUs is 8 on current drivers; prewarm needs 2 per channel. No headroom issue, noted for exotic multi-channel futures.

Phase 3 — Runtime fallback: a wrong selection can never break playback

PHASE 3Effort: small (a few hours) · rides on the existing first-byte gate in servePipe

servePipe already holds the HTTP response open until ffmpeg emits its first fragment, so a hardware job that dies on startup (driver mismatch, exhausted sessions, unplugged eGPU — the failures no probe can promise away) is detectable before any bytes reach the player. This phase turns that gate into a one-shot retry: hardware job exits non-zero with headersSent === false → log the backend and ffmpeg's stderr tail → respawn under the same supervisor key with the software recipe. The viewer sees tune-in take a beat longer; they never see a dead channel.

WhereChange
src/main/stream/server.tsIn servePipe's onExit: if the job used hardware, exited non-zero, and no bytes were sent — respawn once with software args under the same key (a fellBack flag forbids a second retry). Signal-kills (skip, channel change) keep today's behavior; failures after first byte keep today's truncated-body semantics — the MSE pump's retry already covers that. The respawn re-arms the first-fragment gate so a genuine file error still surfaces as a 500 with real stderr.
diagnosticsOne console.error per fallback: backend, episode id, stderr tail. It's the breadcrumb that separates “driver broke” from “file broke” when a report comes in.
tests/stream.test.tsIntegration (skipIf no ffmpeg): settings select VAAPI with RERUN_VAAPI_DEVICE=/dev/null/nope — the request still answers 200 with an ftyp body, and the supervisor saw exactly two spawns for the key. A hard-broken input file under a hardware selection still 500s with ffmpeg's message (fallback doesn't mask real errors).
scripts/soak.mjsAccept a backend argument and run the existing 6-episode soak per available backend — the same harness that guards the stall fix guards this.

Acceptance criteria

  • Bogus VAAPI device: every transcode episode still plays; exactly one fallback log line per job.
  • Prewarm + fallback interact safely: a falling-back prewarm job stays within the two-jobs-per-channel cap (trimGroup semantics unchanged).
  • Soak run green on software, NVENC, and VAAPI on this machine.

Risks & notes

  • Fallback doubles worst-case tune-in latency for the failing backend (~two spawn cycles). Acceptable: it's the failure path, and the log says why.
  • A hardware job that fails mid-stream is not retried server-side — deliberately. The pump's existing reconnect requests a fresh URL with ?t=, and that fresh request gets the fallback logic again.
  • Optional polish, not in scope: surfacing “last transcode fell back to software” in Settings → System.

Verification & rollout

  • Order: Phase 1 and 2 land together in one release if possible (the device answer makes VAAPI trustworthy); Phase 3 immediately after. Each phase is a separate commit with its tests green.
  • Manual matrix on this machine: {HEVC 10-bit 1080p, XviD SD} × {Software, VAAPI, NVENC} × {tune-in, seek, prewarm handoff} — 18 cells, ~20 minutes with the soak harness doing the watching.
  • Quality eyeball: one dark scene and one high-motion scene per backend at the default tier before declaring the CQ/QP mapping final; adjust the two hardware columns only.
  • Rollback: the setting defaults to 'software', which is today's exact command line. Reverting any phase reverts to a working state; no schema or data is at risk (the one migration deletes a dead row).
