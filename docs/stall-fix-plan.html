What is actually happening

Unseekable pipeEvery episode streams as an unbounded fMP4 pipe — no Content-Length, Accept-Ranges: none.
Chromium defersThe progressive loader pauses reading when its buffer is full; the socket sits zero-window.
Connection droppedChromium closes the stalled connection itself (client-side TIME-WAIT) and silently re-requests the same URL.
ffmpeg restarts at 0:00The re-request carries no offset, so the server kills the job and re-encodes from the top.
Frozen until caught upPlayback resumes only when the fresh encode reaches the playhead again — ≈ playhead ÷ 25 seconds of dead air.

Chromium's drop-and-refetch is harmless against a static file server, where a re-fetch costs milliseconds. Against a live transcode it costs a full re-encode — and the deeper into an episode the drop lands, the longer the freeze. Several drops per episode late in a session produce the quantized 30 / 66 / 114 / 159-second pauses below.

The three fixes, and what each one buys

Phase 1 makes the catch-up ~50× cheaper (copying H.264 instead of re-encoding it), so a drop costs a few seconds instead of a minute. Phase 2 removes the drop-and-refetch behavior entirely by taking Chromium's progressive loader out of the pipeline. Phase 3 then uses the freed headroom for gapless handoffs. Phases 1 and 2 are independent of each other; Phase 3 builds on Phase 2.

Phase 1 — Copy the video, transcode only the audio

PHASE 1Effort: small (about half a day) · no schema rebuild · independently shippable

328 of 386 episodes are H.264 video Chromium can decode natively, dragged onto the libx264 path purely by their AC3 audio. The fix routes “video OK, audio not OK” files through the existing remux pipe with -c:v copy and an AAC audio encode decided at serve time from the stored acodec. No new enum value means no CHECK-constraint rebuild on the episodes table.

WhereChange
src/shared/playback.tsdecidePlaybackPath: video supported + audio supported + container direct-safe → direct; video supported (audio supported or not) → remux; video unsupported → transcode. Export needsAudioTranscode(acodec) for the server and the Library UI.
src/main/db/schema.tsMigration 3: one SQL UPDATE re-deriving stored rows — SET playback_path='remux' WHERE vcodec IN (h264, avc1, vp8, vp9, av1) AND playback_path='transcode'. ('remux' already passes the existing CHECK; no table rebuild, no rescan required.)
src/main/stream/server.tsAdd acodec to EpisodeRow. remuxArgs(file, seekS, audioCodecOk, settings): audio OK → -c copy as today; otherwise -c:v copy -c:a aac -b:a <settings.transcodeAudioBitrate>. Same fMP4 movflags, same -ss keyframe seek semantics.
src/renderer/…/Library.tsxOptional polish: REMUX tag gains an “audio → AAC” hint derived from acodec, so the label stays honest.
tests/Extend playback-decision.test.ts (h264+ac3 → remux; hevc+aac → transcode; h264+aac+mp4 → direct) and stream.test.ts (arg builder includes -c:v copy + AAC when acodec is ac3/eac3/dts).

Acceptance criteria

  • Tune-in to an H.264+AC3 file starts in <300ms (copy starts like today's remux).
  • Steady-state ffmpeg CPU per stream drops from ~1600% burst to <50% of one core.
  • Forced connection drop (kill the socket mid-play in the CDP rig) recovers in <5s, not 20–160s.
  • Migration 3 re-labels exactly the 328 rows; a fresh full rescan produces identical labels.

Risks & notes

  • 5.1 AC3 → AAC keeps the source channel count; if a device complains, add -ac 2 behind a setting later.
  • Remuxed sources whose audio is fine but exotic (e.g. Vorbis in MKV) already fail the MP4 mux today — unchanged, out of scope.
  • Stalls are shortened, not eliminated — Chromium still drops and re-fetches. That is Phase 2's job.

Phase 2 — MediaSource playback: own the buffer, keep the connection

PHASE 2Effort: medium (1–2 days) · server output already MSE-compatible (verified: ftyp+moov, then moof/mdat)

The stall class exists because a plain <video src> hands buffering policy to Chromium's progressive loader, which treats an unseekable stream as droppable. The fix: the renderer fetches the same pipe itself and feeds a MediaSource. The app then controls read pace (so the connection is never abandoned), back-buffer eviction, and end-of-stream — and gets a real duration and honest buffered ranges for free. The direct path keeps the plain src and native range seeking.

WhereChange
src/main/stream/server.tsAdd Access-Control-Allow-Origin: * to stream responses — fetch() from the file://-origin renderer is CORS-gated where a media element was not. Loopback bind + Host check still carry the threat model.
src/renderer/src/player/mse.ts (new)The pump: incremental MP4 box scanner (init segment = ftyp+moov; then moof+mdat pairs) → codec strings parsed from stsd (avcC → avc1.PPCCLL, AAC → mp4a.40.2, plus mp3/opus/flac for remuxed audio) → addSourceBuffer → append loop chained on updateend.
buffering policyRead until buffered.end − currentTime ≥ 60s, pause the reader (TCP backpressure throttles ffmpeg exactly as today), resume below 15s. Trim back-buffer beyond 120s behind the playhead; on QuotaExceededError, trim harder and retry. On fetch EOF → endOfStream() → the element's own ended fires.
src/renderer/…/Player.tsxFor remux/transcode: replace src={source.url} with a pump lifecycle effect keyed on source (create on mount/seek, AbortController teardown on change/unmount). Seeks keep today's contract — new URL with ?t=, offset bookkeeping unchanged. retry re-creates the pump. Set mediaSource.duration = episode.durationS so the scrub bar stops guessing.
tests/Box scanner + codec-string extraction as pure-function tests against a tiny fixture generated with ffmpeg's lavfi (same trick as checkCodecs). Pump state machine tested with a scripted fake reader.

Acceptance criteria

  • 3-hour soak in the CDP rig: zero DEMUXER_UNDERFLOW events, exactly one ffmpeg per episode.
  • buffered ahead oscillates between ~15s and ~60s; renderer RSS stays flat across episodes.
  • Seek, skip, retry, channel change, and app quit all kill the old pump and encoder (no orphans in activeKeys()).

Risks & notes

  • Codec-string parsing is the fiddly part; scope is small (H.264 profiles + 4 audio codecs) and fully unit-testable.
  • If an exotic remuxed stream defeats the parser, fall back to plain <video src> for that episode — behavior is then no worse than today.
  • Keep the 20-minute soak script in scripts/ as a regression harness (it found the bug; it should guard the fix).

Phase 3 — Real prewarm: gapless handoff on ended

PHASE 3Effort: medium-large (2–3 days) · depends on Phase 2 · makes the existing prewarmNext setting honest

Today prewarmNext only gates the “up next” toast — nothing is actually prewarmed, and every handoff pays tune-in latency. The fix double-buffers the player: at T−30s the scheduler's pick is committed, the next episode's encoder starts in a second job slot, and a hidden standby <video> buffers its first ~10s. On ended the elements swap instantly.

WhereChange
src/main/stream/ffmpeg.tsJob keys become channel:<id>:<episodeId>; the supervisor allows two live jobs per channel (current + next) and releaseChannel kills by prefix. The one-encoder-per-channel invariant becomes two-with-promotion.
src/main/ipc/handlers.ts + src/shared/ipc.tsNew player.prewarmNext(channelId): runs pickNext (committing cursor/bag/log exactly once) and returns a full NowPlaying for the standby. player.next keeps its meaning for skips with no prewarm pending.
src/renderer/src/store.tsNew pendingNext: NowPlaying | null. At the T−30s window: call prewarmNext, stash the result. On ended or skip while a prewarm is pending: report the finished airing, promote pendingNext — never call pickNext again (that would double-advance the schedule). Leaving the player or changing channel discards pendingNext and releases the channel's jobs.
src/renderer/…/Player.tsxExtract a VideoStage with two stacked <video> elements and an active/standby flip. Standby runs a capped MSE pump (~10–15s target, muted, paused). Swap on ended: play standby, retarget OSD/timecode/volume refs, tear down the old pump. Banner flash already keys on episode id — unchanged.
tests/Scheduler-side: prewarm-then-ended advances state exactly once; prewarm-then-skip also exactly once; prewarm-then-leave releases the lock and the log entry stays incomplete. Store-side: promotion logic with a mocked bridge.

Acceptance criteria

  • Handoff gap (last rendered frame → first frame of next episode) < 250ms in the CDP rig.
  • Play-log picks equal episodes watched — no double-advance under skip/ended/leave races.
  • With prewarmNext off, behavior is exactly the Phase 2 flow.

Risks & notes

  • Committing the pick at T−30s means quitting in the last 30s “spends” one schedule step; identical to today's crash-mid-episode semantics, and acceptable per plan §10.
  • Arc locks: prewarmNext must run through pickNext's transaction (it already handles arc hand-out); peekNext stays display-only.
  • Two encoders can overlap for ≤30s per handoff; after Phase 1 both are stream-copies, so the overlap is nearly free.

Verification & rollout

  • Order: Phase 1 ships alone (smallest, biggest immediate relief). Phase 2 follows and closes the bug class. Phase 3 rides on Phase 2. Each phase is a separate commit with its own tests green.
  • Regression harness: promote the investigation's CDP scripts (monitor.mjs + analyzer) into scripts/soak.mjs — launch muted with --remote-debugging-port, auto-tune, play 6 episodes at 8× rate, fail on any stall > 3s or on >1 encoder per episode.
  • Field check after Phase 1: the play-log query used in the investigation (gap between picks minus episode duration) doubles as a health metric — re-run it after a real evening of viewing; every clean episode reads ≈ +1s.
  • Rollback: Phase 1 is data-safe to revert (labels re-derive on any full rescan). Phase 2 keeps the plain-src code path alive behind the pump fallback. Phase 3 sits behind the existing prewarmNext setting.
